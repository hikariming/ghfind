## 巻頭言：なぜこの3つなのか

2026年、Agent（エージェント）という言葉はバズワードからエンジニアリングの現実へと変わりました。しかし、多くの人がAgentについて語るとき、議論の中心は依然として「もっと上手に答えてくれるか」という点にあります。今号では視点を変えてみたいと思います。**Agentは呼び出されるだけのツールであるべきではなく、存在し続け、動き続け、さらには生活し続けられる実体であるべきだ。**

この考えに沿って、私たちは3つの星を選びました。ちょうどそれらは、内側から外側へと向かうAgentの3層マップを構成しています。

- **yuiju**（yixiaojiu/yuiju）——AIキャラクターが自分の世界でご飯を食べ、学校に通い、散歩し、日記をつけ、ユーザーとは独立した生活を持つことを可能にします。これはAgentの「心」です。
- **lathe**（samzongが立ち上げ、現在はlathe-cli組織でメンテナンス）——既存のAPIをワンクリックで、Agentが安全に呼び出せるCLIコントラクトとSkillに変換し、Agentが実際のシステムを操作できる「手」を与えます。
- **mosoo**（langgenius/mosoo）——Cloudflareネイティブな隔離サンドボックスの中で、Codex、Claude Agent SDK、OpenCodeなどのコーディングAgentをスケールして実行します。これはAgentの「身体」です。

生活を知っている心、仕事ができる手、実際に走れる身体——それぞれが「AIの次の形態」という根本的な問いの一つに答えています。以下は私たちの深掘り分析です。

## 一、yuiju：AIアシスタントではなく、自分の生活を持つ「人」を作る

![yuijuキャラクター「悠ちゃん」のアバター](https://assets.usedify.app/collections/agents-heart-hands-body/yuiju-avatar.webp "図：yuijuプロジェクトのキャラクター「悠ちゃん」のアバター。リポジトリの packages/source/picture/ より")

### 一言レコメンド（作者の言葉）

掘り下げる前に、まずプロジェクト作者本人がyuijuのために書いたレコメンドを引用しましょう。このプロジェクトの魂を的確に言い表していると私たちは考えています。

> yuijuは、仮想世界におけるキャラクターの生活シミュレーションを核としたAIコンパニオンプロジェクトです。継続的に稼働する仮想世界を構築することで、キャラクターに独自の生活の軌跡、社会的関係、成長の経験を持たせ、ユーザーを中心に展開するだけの会話から脱却しています。ゲームデザインの思考を取り入れ、AIコンパニオンを「チャットツール」から「長期的に体験できる世界」へとアップグレードし、ユーザーがコンパニオンシップの中で探索、育成、交流、そして共に成長する楽しさを味わえるようにしています。

### 実際に何をしているのか

主流のAIコンパニオン製品の本質は「ユーザー中心のペルソナエンジン」です。キャラクターは呼べばいつでも応答し、その返答は固定のペルソナテキストからその場で生成されます。yuijuはこのロジックをまったく逆転させました——**世界は会話に先立って存在する**のです。

これはLLM駆動の「キャラクター自律生活シミュレーション」プロジェクトで、AIチャットと「AIタウン」の考え方を融合させています。キャラクターは進み続ける仮想世界の中で、時間、天気、場所、そして自身の状態を感知し、自律的に意思決定を行い、行動を実行します。そして追跡可能な生活の軌跡、記憶、日記、計画を残していきます。ユーザーはQQやFeishuなどのメッセージ入口からキャラクターと交流できますが、チャットはあくまでユーザーがキャラクターの生活を観察し、介入するための窓にすぎません。キャラクターの返答、近況、自発的なシェアはすべて、世界の中で彼女に**実際に起きた**出来事から来ており、その場で即興したテキストではありません。プロジェクトのphilosophyは率直です。AIアシスタントを作るのではなく、自分の生活を持つ「人」を作る。

### 深掘り：なぜ彼女は「生きられる」のか

技術ドキュメントを読んだ後、私たちがyuijuで最も称賛に値すると思ったのは、「キャラクターが自発的に話す」という表層的なことではなく、その背後にあるかなり抑制の効いたエンジニアリング哲学でした。

**第一に、世界エンジンは「tickで進行する」のであり、「会話でトリガーされる」のではありません。** コアモジュール`@yuiju/world`は、継続的に動く2つのプロセスを同時に維持しています。世界状態の進行（時間、天気、シーンの開放状態、リソース量が、ゲームエンジンのように一定間隔で回る）と、キャラクター行動の進行（キャラクターの状態、世界の状態、過去の経歴を読み取り、現在実行可能な行動を計算する）です。**このプロセスはユーザーのメッセージに依存しません**——誰もキャラクターに話しかけなくても、世界は回り続け、彼女は生活し続けます。これこそが「継続的に稼働する世界」という言葉がエンジニアリングに落とし込まれた鍵です。

**第二に、LLMは「意思決定」だけを担当し、「状態の変更」は行いません。** これはシステム全体で最も賢いトレードオフです。「生活」は連続的すぎて、大規模モデルの自由な即興に任せるわけにはいきません。yuijuは複雑な行動をアトミックなActionに分解し、LLMは前置条件を満たした候補Actionの中から選択するだけで、構造化された意思決定結果（どれを選ぶか、なぜか）を返します。実際の状態変化はActionの実行ロジックによって行われ、行動記録として蓄積され、後の記憶、日記、メッセージ返信に使われます。言い換えれば、モデルは「人生の道のりにおける選択者」であり、システムは「生活を事実として記録する台帳」です。これによりキャラクターの行動の暴走を防ぎつつ、あらゆる経験を追跡・再生可能にしています。

**第三に、記憶はチャットログの積み上げではなく、階層化されています。** メッセージコンテキストは無限に連結されません。システムは直近の生メッセージ、ローリングサマリー、自然な会話ウィンドウを同時に維持し、会話ウィンドウは適切な境界でMemory Episodeとして沈殿し、キャラクターの記憶を更新します。キャラクターはそれによって「今日のことを覚えている」ことができ、毎回ゼロから自己紹介し直すことがありません。作者はブログでも率直に認めています。記憶モジュールは依然としてJSONで保存され、LLMが自己更新しており、時折間違えると。こうした誠実さこそ、オープンソースプロジェクトの最も心を動かされる部分です。

**第四に、ゲームデザインの思考が全面的に浸透しています。** 動的な天気システムが日常を固定スクリプトから解放し、キャラクターは長期・短期の計画を持つことができ、ユーザーの今の入力に受動的に応えるだけではありません。生活の中で語る価値のあることが起きれば、彼女は適切なタイミングで自発的にシェアします。永遠にあなたが話し始めるのを待つのではなく。作者自身はプロジェクトを「状態、行動、記憶、生活のリズムを持つAIキャラクターシステム」と紹介しています——これは「仮想生命」の最も簡潔な定義です。

![yuijuシステムアーキテクチャ図](https://assets.usedify.app/collections/agents-heart-hands-body/yuiju-architecture.png "図：yuijuシステムアーキテクチャ——@yuiju/world 世界エンジンが世界状態とキャラクター行動を並行して進行させ、LLMはActionの意思決定のみを行う")

### エディターコメント

yuijuは、多くのAIコンパニオンプロジェクトが避けてきた問いに答えています。**AIはあなたがいないときにも、自分の生活を持つことができるのか？** コンパニオンシップを「あなたが私を召喚する」から「私たちはそれぞれ生活し、時々出会う」へとアップグレードし、感情のつながりをその場で生成される甘い言葉ではなく、本物の共同経験の上に築き上げています。プロジェクトはまだ初期段階で、記憶モジュールなどの部分も継続的に磨かれていますが、それが提供する方向性——ゲームエンジン式の決定論的フレームワークでLLMの自由度を制約し、受け止めるというアプローチ——は、AIキャラクター分野全体にとって非常に参考価値の高いものです。『あつまれ どうぶつの森』が好きな人、育成やコンパニオンシップの感覚が好きな読者は、ぜひすぐにWebページで一度体験してみてください（`yuiju-web.yixiaojiu.top`）。最後に悠ちゃんのスタンプを貼って、彼女の「ちょっとした拗ね顔」を感じてください。

## 二、lathe：APIからワンクリックでAgentの「手」を生やす

![lathe ロゴ](https://assets.usedify.app/collections/agents-heart-hands-body/lathe-logo.png "図：latheプロジェクトのロゴ。リポジトリの docs/images/ より")

### これは何か

latheはAgent向けのAPI-to-CLIジェネレーターです。Swagger 2.0、OpenAPI 3、`google.api.http`アノテーション付きのprotobuf、さらにはGraphQLスキーマから、**シングルバイナリで本番級**のCobra CLIを生成し、構造化されたコマンドカタログと生成されたSkillガイドを付属させます。プロジェクトはsamzongが立ち上げ、現在はlathe-cli組織でメンテナンスされており、MITライセンスです。まだ若いプロジェクトですが、イテレーションの速度は驚異的です。

作者の動機は素朴で、そして心を動かされます——「旧世界の既存システムをAgentに直接接続する」。ほとんどのチームはAPIがないわけではありません。歴史あるAPIが山のようにあるのに、それらをAIに安全かつ確実に操作させる方法に苦労しているのです。

### コア哲学：Specが真実、Catalogがコントラクト

latheの設計全体は2つの文に凝縮されます。

1. **API仕様が唯一の真実の情報源である。** pinした上流specを宣言し（タグで固定、commit SHAに解決、浮動ブランチは拒否）、CLIの識別情報（`cli.yaml`）とモジュールの出所（`specs/sources.yaml`）を宣言し、必要に応じてoverlayでヘルプテキストを磨き上げます。APIが変わったら、再生成するだけです。「CLIを手書きして、一生drift（ドリフト）と戦い続ける」という宿命からの解放です。
2. **生成されるCLIは単なるシェルではなく、Agentが機械的に消費できるコントラクトである。** これこそが、latheと通常のAPIラッパーツールとの本質的な違いです。

### 深掘り：「Agentは推測しない」ために設計された一式のプロトコル

READMEを読むと、latheが「AgentがCLIを安全に使う方法」という問題を異例のほど丁寧に分解していることに気づくでしょう。

- **発見**：`search "<intent>" --json`が自然言語の意図で候補コマンドを探し、`commands --json`が完全なコマンドカタログを出力し、`commands show <path>`で特定コマンドのflags、body、認証、HTTPメソッド、出力のヒントを確認できます——すべての情報は構造化されたJSONです。
- **プリフライト**：`auth status --hostname <host>`で保護されたコマンドを呼ぶ前にクレデンシャルを確認し、`--dry-run`は実際には送信せずに送信予定のリクエスト（マスク済みのheadersとbodyを含む）を表示し、Agentが実行前にすべてを照合できるようにします。
- **実行**：`--file` / `--set` / `--set-str`でリクエストボディを構築し、`-o table|json|yaml|raw`が機械可読な出力を提供し、列挙値のバリデーション、ページネーション、ストリーミングまで一通り揃っています。
- **生成されるSkill**：codegenはデフォルトで`skills/<cli-name>/`ディレクトリを書き出します。これは「このCLIのAgent操作マニュアル」に相当し（コマンドの発見方法、カタログの確認、認証のプリフライト、bodyの構築、出力フォーマットの選択）、バイナリにパッキングすることも可能です（`<cli> skill install`）。ランタイムのカタログが真実であり続け、SkillはAgentに使い方を教える入門ガイドです。

さらに、言及に値するエンジニアリングの詳細が3つあります。すべての生成モジュールは**同一のランタイム**を共有し（認証、リクエスト構築、出力、ページネーション、ストリーミング、エラーハンドリングの挙動が一貫）、**overlayレイヤー**は上流specや生成されたGoコードを変更せずに、コマンドの非表示・無視、パラメータの修正、ショートカットコマンドの追加を可能にし、2段階パイプライン（`specsync`がspecを取得・固定 → `codegen`が統一IRに正規化してレンダリング）が再現性を保証します。

![lathe アーキテクチャ図](https://assets.usedify.app/collections/agents-heart-hands-body/lathe-architecture.png "図：latheの生成フロー——specの固定同期 → codegenによる正規化レンダリング → CLIと付属Skillの生成")

### なぜ今なのか：CLIがAgentの事実上のインターフェースになりつつある

latheは非常に興味深い業界の波に乗っています。VercelのCEOは「CLIs are the de-facto MCPs for agents」（CLIはAgentの事実上のツールプロトコルだ）と明言し、PerplexityのCTOやY CombinatorのトップであるGarry Tanも同時期にCLI路線を公に支持しており、中国語圏コミュニティでは一時「MCPは死んだ」という声まで上がりました。一方で、FeishuのようなベンダーはCLIとMCP Serverの両方をオープンソースプロジェクトとして同時にメンテナンスしています。この「Agentインターフェース戦争」の分岐点において、latheの選択は賢明です。**CLIかMCPかどちらが勝つかを議論するのではなく、「APIからAgentフレンドリーなCLIを生成する」こと自体を自動化されたパイプラインに仕立て上げ、付属のSkillまで一緒に生成するのです。**

### エディターコメント

latheが向いているのは2種類の人です。一つは、大量のSwagger/OpenAPI/proto/GraphQLを抱えていて、既存システムをAgentに接続したいチーム——「旧世界を新世界につなげる」コストを最も低く抑えられるツールの一つです。もう一つは、「一つのバイナリで、人間は使え、Agentは安全チェックできる」というエンジニアリングの美学を愛する開発者です。latheは「Agentは推測すべきでない」というスローガンを、実行可能な6ステップのループ（検索 → 確認 → 認証プリフライト → dry-run → 実行 → 構造化出力）に変えました。これが最も堅実な貢献です。

## 三、mosoo：coding agentにスケールして動ける「家」を

![mosoo バナー](https://assets.usedify.app/collections/agents-heart-hands-body/mosoo-banner.png "図：mosoo公式バナー（2400×1260）。リポジトリの docs/assets/ より")

### これは何か

mosooはオープンソースのCloudflareネイティブな**coding agentランタイム**です。OpenAI Codex、Claude Agent SDK、OpenCodeなどのコーディングAgentを、APIエンドポイントの背後にある相互に隔離されたAI Agentサンドボックスの中で実行し、検査・再生・再開可能な実行記録を提供します。これは**LangGenius——つまりオープンソースのLLMアプリケーションプラットフォームDifyの背後にいるチーム**から生まれました。そこからそのエンジニアリング指向は最初から決まっていました。個人の趣味の玩具ではなく、「Agentを自分のプロダクトに組み込みたい」開発者のためのインフラです。Apache 2.0ライセンス。

### どのレイヤーの痛みを解決するのか

自分のプロダクトでcoding agentを使おうとすると、通常は同じ壁にぶつかります。agentランタイム、サンドボックスサービス、セッションストレージ、ファイルパイプライン、Agent APIを自分でメンテナンスしなければならない——しかも新しいagent harness（Codex、Claude、OpenCode……）を追加するたびに、これら全部をやり直す羽目になります。mosooのポジショニングは、この一塊をまるごと一つの**コントロールプレーン**に畳み込むことです。あなたのアプリケーションはあなたのものであり、プロダクトの振る舞いとエンドユーザー体験をあなたが所有します。mosooはAgentの実行とライフサイクルだけを担当します。自らを控えめに位置づけています——「アプリのデプロイは別のAlphaサーフェスであり、コアプロダクトのコントラクトではない」。

### 深掘り：Agentは「一回の呼び出し」から「存在し続ける実行ライン」へ

mosooの5つのコア機能は、「agentのプロダクト化」に必要なすべての環に完全に対応しています。

- **統一されたランタイムとコントロールプレーン**：3種類のagent harnessが同じランタイムプロトコルの下に正規化され、ツールごとに3セットの統合を書く必要がありません。
- **Agent API**：信頼できるバックエンドから、Agentの作業をstart / follow / continue / stop / archive / deleteできます——Agentの作業はあなたがオーケストレーションできるものです。
- **隔離されたAI Agentサンドボックス**：レスポンスとツール活動をストリーミングで返し、権限リクエストを処理し、作業をキャンセルし、隔離された実行環境で診断情報を確認できます——「agentをユーザーに渡す」ことを安全でコントロール可能にします。
- **永続的な作業（Durable Work）**：Threads、Runs、イベント、マネージドファイルが複数回の実行をまたいで保持されます。これが最も本質的な理念です。Agentは使い捨ての呼び出しではなく、中断したところから再開できる実行ラインです。
- **オブザーバビリティ**：Runの状態、再生可能な活動、診断、使用量の推計——コンプライアンス監査ではなく、運用上の可視性です。

周辺エコシステムもすでに骨格ができています。`mosoo-agent-driver`、`mosoo-connector`、そして興味深い`mosoo-skills`（20個のプロジェクト対応coding-agent skills。うち16個は公開上流の無修正コピー、4個はmosooがメンテナンスし、上流の更新でプロジェクト固有のガードレールが消えないよう、意図的に同期マニフェストから除外されています）。技術スタックとしては、Cloudflare Workers + D1 + R2の上でネイティブに動作し、自分のアカウントにセルフホストできます。

### リスク警告（エディターからの正直な注意）

読者の皆さんにお伝えしなければなりません。**mosooは現在Alpha段階です。** 公式READMEには、ホステッドランタイムとAgent APIはリリース済みでリポジトリのテストでカバーされているものの、「本番での信頼性と外部での採用はまだ検証されていない」と明記されており、公開APIとプロダクトの振る舞いは今後変わる可能性があります。したがって、いち早く試してagentプロダクト化のプロトタイプを探索したい開発者には適していますが、本番のクリティカルパスに直接賭ける場合は、必ずリスクを評価し、適切に隔離してください。

### エディターコメント

mosooの意義は、「coding agentを動かす」ことをバラバラなDIYの組み立て作業から、デプロイ可能で、観測可能で、オーケストレーション可能なインフラへと変えたことにあります。業界全体が「Agentをどうプロダクトにするか」を議論している中、DifyチームはLLMアプリケーションプラットフォームでの蓄積を活かし、Cloudflareネイティブな模範解答——隔離サンドボックス、永続セッション、統一API、必要時の再開——を提示しました。Codex / Claude Agent SDK / OpenCodeを自社プロダクトへと拡張しようとしているチームにとって、比較リストに入れて真剣に評価する価値があります。

第1号では、一見無関係な3つの星を同じページに並べましたが、実は伝えたかったのは一つのことです。**AIの次の形態は、おそらくもっと賢いダイアログボックスではなく、走れて、働けて、生活できる「実体」です。** yuijuはそれに生活を与え、latheは両手を与え、mosooは身体を与えました——それぞれが体験、インターフェース、インフラという3つのレイヤーを代表しており、真の未来のプロダクトは、おそらくこの3つすべてを同時に備えることになるでしょう。
