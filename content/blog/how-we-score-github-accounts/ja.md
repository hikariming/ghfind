**一言で言うと:** このスコアは、たった一つの実用的な問いに答えます——*この開発者は公開の場で、どれだけ本物で価値のある仕事をしてきたのか？* そしてその答えを、毎回同じ方法で、公開データだけを使い、すべてのルールを公開したうえで返します。この記事では専門用語を使わず、その数字がどう作られるのかを説明します。

## そもそもなぜスコアなのか

ますます多くの判断が、誰かの GitHub をちらっと見ることに頼るようになっています。採用担当者は通話の前にプロフィールに目を通す。メンテナは見知らぬ人の Pull Request をレビューする価値があるか判断する。ディレクトリ系のサイトは「どれだけ立派に見えるか」でアカウントを並べる。こうした用途のどれもが、その信号を*偽装する*動機を生みます——そして人気のある信号ほど偽装は簡単です。star は買える。フォロワーは交換できる。一行だけの Pull Request を午後いっぱいで百個開けば、自称「オープンソース貢献者」の出来上がりです。

だから役に立つスコアは、大きくて派手な数字を足し合わせるわけにはいきません。仕事そのものを測り、買える数字は無視しなければなりません。以下のすべての設計は、この一つの考えから導かれています。

## 唯一の原則：拍手ではなく仕事を量る

スコアの背後にあるエンジンは **devscore** といいます。そのルールは短いものです：*開発者が実際に作ったものを、それがどれだけ重要か、そしてそのうちどれだけが本人のものかで重み付けして採点する。*

- **star とフォロワーは一切カウントしません。** 少しだけでも、上限付きでもなく——ゼロです。これらは注目度を測るものであり、注目度は安く買えます。
- **Pull Request の数もカウントしません。** エンジンが測るのはあなたが書いたコミットとその変更内容なので、一行だけの PR を百個出しても、一行の変更が百個あるだけです。
- **カウントされるのは、人が使うプロジェクトに入ったコードです。** 自分のプロジェクトは他の人が使っていればカウントされ、他人のプロジェクトでの仕事は独立したメンテナが受け入れていればカウントされます。

## プロジェクトの価値

devscore はリポジトリごとに、まずそのプロジェクトがどれだけ重要かを問います。star は決して見ません。見るのは、他の人が実際に*何かをする*必要があるため偽装しにくい信号です：

- そこにコードを書いた**他のコントリビューター**、
- **下流の依存先**——それに依存しているパッケージ、
- **外部の issue 作成者**——問題を報告するほどそれを使っている人、
- **fork**——ただしこれらの中で最も安く水増しできるため割り引かれます。

普及度が10倍になるごとに同じだけ加算されるので、数千人のコントリビューターを抱えるカーネルは20人のライブラリをはるかに上回り、作者と数人の友人しか使っていないプロジェクトは底辺近くにとどまります。他に誰も使っていないプロジェクトでは、そこでの仕事のごく一部しか残りません——自分のために何かを作るのはまったく問題ありませんが、それはまだ他の人が頼っているものではありません。

star ばかりでユーザーのいないプロジェクトは特別扱いされます。**話題先行プロジェクト**——star は多いのにコントリビューターも issue 作成者も依存先もほとんどない、あるいは宣伝による急増のあと沈黙した——には、プロジェクトの評価がまったく付きません。

## そのうちどれだけがあなたのものか

次に devscore は、そのプロジェクトの仕事のうちどれだけがあなたのものかを問います。コミットに占めるあなたの比率と、筆頭作者と比べたあなたの立ち位置を組み合わせるので、大きなプロジェクトの共同リードは比率がそこそこでも作者とみなされ、支配的なリードの後ろにいる遠いコントリビューターはそうみなされません。自分のコミットが数千あれば、プロジェクトの規模にかかわらず作者とみなされます。

そのうえで仕事そのものを測ります：いくつのコミットを入れたか、それが何を変えたか（コアのコードはドキュメントや雑務より重く、メンテナが受け入れた大きな変更は小さな変更より重い）、そして仕事が何か月続いたか。機械生成に見えるコミット履歴——すべてのコミットが同じ時刻、すべての変更が同じ形——は割り引かれます。

## 他人のプロジェクト：受け入れられた仕事だけがカウントされる

他人のリポジトリでの仕事は、GitHub で最もピアレビューに近いものです——ただし独立した誰かが実際にレビューした場合に限ります。そこで devscore は外部での仕事を、**独立したメンテナが受け入れた分だけ**カウントします：

- プロジェクトの筆頭作者がマージした PR は満額でカウント、
- コードを一行も書いていない人が素通しした PR は半分、
- 自分でマージした PR や、あなたの PR をマージし返してくれる取引相手がマージした PR はゼロ、
- 報酬キャンペーン中にまとめてマージされた大量の大きな単独 PR は割り引かれます。

他人のコードをレビューしてマージすることも本物の仕事です。**メンテナ**——自己申告ではなく、そのリポジトリでのあなたの役割を示す GitHub 自身の記録で検証されたもの——はその仕事の評価を得ますし、他人のプロジェクトであなたが行うコードレビューもカウントされます。

## 時間：一時の爆発ではなく、継続した年数

最後に、devscore はこれを何年も続けることに報います。カウントするのは**継続的なコーディング年数**です：各暦年は1回だけカウントされ（上限12か月分のコーディング）、1年分を60個の小さなリポジトリに分散させても1年のままです。古い仕事は半減期3年で薄れていきます（ただし下限があるので、長いキャリアが消えることはありません）。

これらすべてが 0 から 100 までの一本のなめらかな曲線にまとめられ、頂点には余裕が残されているので、最上位の人たちが 100 で横並びにならずに差がつきます。最も強い役割が勝ちます：開発者としてもメンテナとしても評価され、良い方がカウントされます。

## 偽物を捕まえる

ほとんどの水増しにはペナルティすら必要ありません。それが生み出す信号——star、フォロワー、PR 数、セルフマージ——はもともと点にならないからです。明示的な**上限**がかかるのは2つのパターンで、最後に適用されます：

- **低品質 PR の大量投稿。** 最悪の12か月の間に、他人のプロジェクトへの PR が多数却下または取り下げられ——少なくとも独立にマージされた数と同じくらい——しかも次のうち2つ以上が伴う場合：テンプレ化したタイトル、重複した投稿、多数のリポジトリにまたがる1週間の集中投稿、数千行の巨大な PR。
- **インフルエンサー型のパターン。** 他の人が受け入れたエンジニアリングとは釣り合わない数百人のフォロワーがいて、メンテナンスしているプロジェクトも、実質的な自分のプロジェクトもない。

上限がかかったスコアは 20〜35 の範囲に押し込まれ、その中では元の仕事の量で順序が保たれます。重要なのは、どちらの上限も履歴全体にわたる*パターン*に対して発動するということです——却下された PR が一つある、あるいは本物のコードも出している人気アカウントであることは、まったく普通のことです。

## プロフィールに表示される6つの数字

合計点は devscore のスコアです。読みやすくするため、各プロフィールには devscore のファクターから導かれる6つの**表示用の次元**も表示されます。これらはスコアを説明するものであって、足し合わせてスコアを作るものではありません。

| 次元 | 満点 | 何を示すか |
|---|---|---|
| **貢献の質** | 27 | 他人のプロジェクトで独立に受け入れられた仕事と、そこであなたが行うコードレビュー |
| **エコシステムへの影響** | 20 | リポジトリ全体でのあなたの仕事の重み、または検証済みのメンテナとしての役割——いずれか高い方 |
| **オリジナルプロジェクトの質** | 18 | あなたの看板：あなたが所有または主導する最も強いエンジニアリングプロジェクト |
| **活動の真正性** | 17 | あなたの仕事のうちどれだけが最近のものか。水増しの上限が適用されると大きく削られる |
| **アカウントの成熟度** | 10 | 継続的なコーディング年数 |
| **コミュニティ影響力** | 8 | メンテナがあなたの PR を却下せずにマージする頻度と、あなたが行うレビュー——フォロワーは決して含まない |

## 最後の数字が意味するもの

| スコア | 段位 | 意味 |
|---|---|---|
| 90–100 | **夯（神）** | 伝説級——殿堂入りの仕事。 |
| 80–89 | **顶级（エリート）** | トップクラスの開発者。 |
| 70–79 | **人上人（堅実）** | 良質な貢献者——信頼に値する。 |
| 40–69 | **NPC** | 平凡なアカウント——特徴が凡庸か、判断がつかない。 |
| 0–39 | **拉完了（お手上げ）** | 公開された仕事がほとんどない——または上限がかかった水増しパターン。 |

段位の名前はわざと少しふざけています——もともとロースト用のツールとして始まったので——が、その背後の計算は誰に対しても同じです。

## 正直に言う：このスコアが**そうでない**もの

- **公開された活動しか見えません。** 会社のプライベートリポジトリで素晴らしい仕事をしている人は、ここでは薄く見えることがあります。低スコアは*公開された*足跡についての言明であって、その人への判決ではありません。各スコアには、それがどれだけの公開証拠に基づいているかを示す信頼度が付いています。
- **出発点であって、裁判官ではありません。** この数字は人が優先順位をつけるのを助けるためのもの——どの見知らぬ人の PR を先に見るか、どのプロフィールを丁寧に読むか——であって、誰かを自動で却下するためのものではありません。スコアの背後にある証拠のほうが、スコア自体より重要です。
- **古い仕事は、ゆっくり薄れます。** 最近の年は大昔の履歴より重くカウントされますが、長い実績が消し去られることはありません。

## オープンソースです——自分で動かせます

どれもブラックボックスではありません。ループの中にモデルはなく、隠れた重み付けもありません：同じ公開データからは常に同じスコアが出て、上で説明したすべてのルール——すべての重み、すべてのしきい値、すべての上限——は AGPL ライセンスで公開されています。

- **コードを読む：** [github.com/hikariming/ghfind](https://github.com/hikariming/ghfind)（エンジンは `src/lib/devscore` にあります）
- **ローカルで動かす**なら `npx @hikariming/ghfind score <user> --local` と自分の GitHub トークンで——何もマシンの外に出ません——または公開 API を呼ぶ（[OpenAPI 仕様](https://ghfind.com/openapi.json)）。
- **単一アカウントを採点する**なら、ブラウザで [ghfind.com](https://ghfind.com) を開くだけ。

重みやしきい値に異論があれば、それが正確に何なのかを読み、変更し、その効果を確かめられます。人が検証できない信頼スコアにはあまり価値がありません——だから、検証できるスコアを作りました。
