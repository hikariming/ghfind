**一句话：** 这个分数只回答一个很实际的问题——*这个开发者在公开场合到底做了多少真实、有价值的工作？* 而且它每次都用同一套规则、只看公开数据、把所有规则都摆在明面上来回答。这篇文章不讲黑话，把这个数字是怎么算出来的讲清楚。

## 为什么要有一个分数

越来越多的判断，就靠瞄一眼某人的 GitHub。招聘的人在电话前先扫一遍主页；维护者要决定一个陌生人的 Pull Request 值不值得看；目录类网站按"看上去有多牛"给账号排序。每一种用法，都在制造伪造这些信号的动机——而最显眼的信号，恰恰最容易造假。star 能买，粉丝能互换，一个下午开一百个只改一行的 Pull Request，就能自称"开源贡献者"。

所以一个有用的分数，不能把这些又大又亮的数字加起来。它必须去称量工作本身，并且无视那些能花钱买到的数字。下面每一个设计决定，都源于这一个想法。

## 唯一的原则：称工作，不数掌声

分数背后的引擎叫 **devscore**。它的规则很短：*衡量一个开发者真正做出来的东西，按它有多重要、其中有多少是他本人的来加权。*

- **star 和粉丝一律不计分。** 不是少算、也不是封顶——就是零。它们衡量的是关注度，而关注度很便宜。
- **PR 的数量也不计分。** 引擎看的是你写的提交以及它们改了什么，所以一百个只改一行的 PR，仍然只是一百个一行的改动。
- **真正算数的，是落进有人在用的项目里的代码。** 你自己的项目，有别人在用才算数；你在别人项目里的工作，被独立维护者接受了才算数。

## 一个项目值多少

对每个仓库，devscore 先问：这个项目有多重要？它从不看 star，而是看那些需要别人*真的做点什么*才会出现、因此很难造假的信号：

- **其他贡献者**——在里面写过代码的人；
- **下游依赖**——依赖它的软件包；
- **外部 issue 作者**——用得足够多、会来报问题的人；
- **fork 数**——打了折扣，因为它是这些信号里最容易刷的。

采用度每上一个数量级，加的分数相同。所以一个有上千名贡献者的内核，会明显高于一个只有二十人的库；而只有作者本人和几个朋友在用的项目，会停在底部附近。没有其他人使用的项目，里面的工作只保留一小部分分量——给自己造东西没问题，但它还不是别人依赖的东西。

全是 star、没有用户的项目会被特别对待。**炒作型项目**——star 很多，却几乎没有贡献者、issue 作者或下游依赖，或者经历一次突击推广后就沉寂——拿不到任何项目分。

## 其中有多少是你的

接下来，devscore 问：这个项目的工作里有多少是你的？它把你的提交占比和你相对于主要作者的地位结合起来看：一个大项目的共同负责人，即使占比不高也算作者；而远远落后于主力作者的零星贡献者则不算。你自己的上千次提交，无论项目多大都算作者身份。

然后它称量工作本身：你落地了多少提交、改了什么（核心代码比文档或杂务更重；被维护者接受的大改动比小改动更重）、以及这些工作持续了几个月。看起来像机器生成的提交历史——每次都在同一个小时提交、每个改动的形状都一样——会被降权。

## 别人的项目：只算被接受的工作

在别人的仓库里做贡献，是 GitHub 上最接近同行评审的东西——但前提是真的有独立的人审过。所以 devscore 对外部工作**只按被独立维护者接受的程度计分**：

- 由项目主要作者合并的 PR，全额计入；
- 由一个自己没写过这份代码的人随手放行的，算一半；
- 你自己合并的 PR，或者由互相合并对方 PR 的"交易伙伴"合并的，一分不算；
- 在奖励活动期间被成批合并的几十个大型独立 PR，会打折扣。

审核并合并别人的代码，本身也是真实的工作。**维护者**——由 GitHub 自己记录的你在该仓库中的角色来验证，从不采信自称——这部分工作会被计分；你在别人项目里做的代码评审也同样计入。

## 时间：持续的年份，而不是一阵子

最后，devscore 奖励长年坚持。它统计**持续编码的年数**：每个自然年只算一次、最多按十二个编码月计，所以把一年的工作摊到六十个小仓库，仍然只是一年。较早的工作按三年半衰期递减（但有下限，漫长的职业生涯不会被抹掉）。

所有这些最后汇成一条从 0 到 100 的平滑曲线，顶部留有空间，让最强的人能拉开差距，而不是都挤在 100 分。一个人同时会以开发者和维护者两种身份被评估，取两者中更强的那个。

## 抓住造假的人

大多数刷量根本不需要扣分，因为它们制造出来的信号——star、粉丝、PR 数量、自己合并自己——本来就不得分。只有两种模式会被明确**封顶**，并且在最后一步生效：

- **批量低质 PR。** 在最糟糕的十二个月里，给别人项目提的 PR 大量被拒绝或撤回——至少与被独立合并的一样多——并且至少伴随以下两项：模板化标题、重复提交、一周之内刷遍多个仓库、上千行的巨型 PR。
- **网红模式。** 数百名粉丝，却与被别人接受的工程贡献完全不成比例，同时没有维护中的项目，也没有分量足够的自有项目。

被封顶的分数会被压到 20–35 分之间，并仍按底层工作量排序。关键在于，两条封顶规则针对的都是整段历史中的*模式*——被拒一个 PR，或者一个本身也在写真代码的热门账号，都完全正常。

## 主页上的六个数字

总分就是 devscore 给出的分数。为了便于阅读，每个主页还会展示从 devscore 因子换算出的六个**展示维度**。它们用来解释分数，而不是加起来得出分数。

| 维度 | 满分 | 它展示的是 |
|---|---|---|
| **贡献质量** | 27 | 在别人项目里被独立接受的工作，加上你在那里做的代码评审 |
| **生态影响力** | 20 | 你在各个仓库工作的总分量，或经验证的维护者身份——取较高者 |
| **原创项目质量** | 18 | 你的旗舰：你拥有或主导的最强工程项目 |
| **活跃真实性** | 17 | 你的工作中近几年所占的比例；触发刷量封顶时会被大幅压低 |
| **账号成熟度** | 10 | 持续编码的年数 |
| **社区影响力** | 8 | 维护者合并而非拒绝你 PR 的比例，加上你做的评审——从不看粉丝 |

## 最终数字意味着什么

| 分数 | 段位 | 含义 |
|---|---|---|
| 90–100 | **夯** | 封神——殿堂级的工作。 |
| 80–89 | **顶级** | 顶级开发者。 |
| 70–79 | **人上人** | 优质贡献者——值得信任。 |
| 40–69 | **NPC** | 普通账号——特征平庸或不明确。 |
| 0–39 | **拉完了** | 公开工作很少——或者被封顶的刷量模式。 |

段位名字故意起得有点皮——这个项目最初是个吐槽工具——但背后的算法对每个人都一样。

## 老实说，这个分数*不是*什么

- **它只看得到公开活动。** 在公司私有仓库里干得很出色的人，在这里可能显得很单薄。低分描述的是*公开*足迹，而不是对这个人的评判。每个分数都附带一个置信度，说明它依托了多少公开证据。
- **它是起点，不是法官。** 这个数字是用来帮人排优先级的——先看哪个陌生人的 PR、哪个主页值得细读——而不是用来自动拒绝任何人。分数背后的证据比分数本身更重要。
- **旧的工作会慢慢褪色。** 近几年比久远的历史更重，但长期的积累永远不会被清零。

## 它是开源的——自己跑一遍

这里面没有任何黑箱。流程中没有模型，也没有隐藏的权重：相同的公开数据永远得到相同的分数，上面描述的每一条规则——每个权重、每个阈值、每个封顶——都按 AGPL 协议公开。

- **读代码：** [github.com/hikariming/ghfind](https://github.com/hikariming/ghfind)（引擎在 `src/lib/devscore` 目录）
- **在本地运行：** 用 `npx @hikariming/ghfind score <user> --local` 加上你自己的 GitHub token——数据不会离开你的机器——或者调用公开 API（[OpenAPI 规范](https://ghfind.com/openapi.json)）。
- **给单个账号打分：** 在浏览器里打开 [ghfind.com](https://ghfind.com)。

如果你不认同某个权重或阈值，你可以准确地读到它是多少、改掉它、看看效果。一个人们无法检查的可信度分数不值多少钱——所以我们做了一个你可以检查的。
