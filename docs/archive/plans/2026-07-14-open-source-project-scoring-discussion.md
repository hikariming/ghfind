# 开源项目评分产品讨论总结

## 一、产品目标

做一个类似 ghfind 的开源项目分析与评分产品，但评分对象从“开发者账号”变成“开源项目”。

它的核心目的不是寻找 stars 最多、团队最大、工程规范最完整的项目，而是：

> 发现真正解决实际问题、好用但缺乏曝光和宣发渠道的开源项目。

第一版只提供两个榜单：

- 宝藏项目榜：突出产品价值高、实际好用，但曝光不足的项目。
- 经典项目榜：收录经过长期验证、仍然值得使用和参考的成熟项目。

暂不单独拆分“新锐”“小而美”“快速进步”等榜单。它们先作为项目标签和筛选条件存在；只有后续项目数量和用户需求足够明确时，再从“宝藏项目榜”中分流，避免首版入口过多。

## 二、核心评分原则

项目规模不等于产品价值。

大型企业项目和小型甜点工具不能使用完全相同的检查清单，但都可以回答同一个核心问题：

> 这个项目是否用合适的复杂度，有效解决了一个真实问题？

因此：

- 小项目不会因为维护者少、没有企业级安全体系而天然低分。
- 大型项目不会因为代码多、贡献者多、功能多而天然高分。
- 一个简单但极其实用的工具，可以获得很高的产品分。
- 一个庞大但难以部署、难以理解、核心流程不好用的企业系统，产品分应该较低。

“项目雄心”和“实现难度”可以作为描述性标签，但不直接奖励复杂度。

## 三、评分前先识别项目类型

分析 Agent 首先要建立项目的“产品契约”：

```text
目标用户是谁？
用户在什么场景下使用？
它解决什么痛点？
用户以前如何解决？
项目承诺提供什么结果？
它属于哪种项目？
目前处于什么生命周期？
```

项目类型包括但不限于：

- 微型工具、CLI
- SDK、开发库
- Web 应用
- 桌面应用
- 框架、平台
- 数据库、基础设施
- 模板、脚手架
- 大型企业级系统

不同项目使用不同的具体判断标准：

- CLI 看安装速度、默认体验、核心命令和错误提示。
- SDK 看 API 设计、兼容性、文档和集成成本。
- Web 应用看部署、交互、核心流程和实际可用性。
- 企业系统看复杂场景能否真正完成，而不是只看功能数量。
- 模板项目不会因为缺少频繁 release 被机械扣分。

## 四、当前主评分模型

主分定义为“项目价值分”，共 100 分。

| 维度 | 分值 | 判断内容 |
| --- | ---: | --- |
| 需求痛点 | 25 | 问题是否真实、高频，现有解决方式是否足够难受 |
| 解决效果 | 25 | 项目是否真正解决了它承诺的问题 |
| 上手与体验 | 25 | 是否容易安装、运行，并完成第一次核心任务 |
| 范围与价值密度 | 15 | 是否用恰当的复杂度解决问题，是否过度设计 |
| 真实使用证据 | 10 | dependents、下载、用户案例、Issue 内容和实际反馈 |

价值密度是“小而美”项目的重要优势：

```text
价值密度 = 用户获得的实际价值 / 理解与使用成本
```

一个几百行代码、一条命令解决高频问题的项目，完全可以在产品维度拿到 90 分以上。

## 五、工程指标的定位

测试、CI、类型检查、代码结构、构建稳定性等仍然重要，也有大量现成工具可以复用。

但它们不再直接按照固定规则加分，而是作为 Codex 的分析工具和证据来源。

例如：

- 小型 CLI 没有完整 CI，不一定是严重问题。
- 数据库缺乏可靠测试，可能是重大问题。
- Web 工具测试较少，但实际操作稳定，仍可能有很高产品分。
- 企业系统测试很多，但官方部署流程跑不通，产品分仍然应该较低。

原则是：

> 工程指标只有影响项目承诺和实际体验时，才应该显著影响主分。

## 六、维护状态的处理

不再使用“最近 commit 数”“维护者数量”直接打维护分。

先由 Codex 判断项目的生命周期：

```text
active_evolution      持续快速开发
stable_maintenance    稳定维护
feature_complete      功能已经完成
experimental          实验性项目
abandoned             实质废弃
```

然后判断当前状态是否适合该项目。

例如：

- 一个两年没更新的小工具，今天仍能正常安装和运行，不应该扣分。
- 一个依赖快速变化生态的 AI 平台，两年没更新，很可能已经不可用。
- 单人维护不是问题，关键是项目是否仍然兑现承诺。
- 大量维护者也不应该直接加分。

## 七、安全、License 与供应链

安全与供应链不再作为固定的 15 分主维度。

原因是：

- 大公司和企业孵化项目天然拥有法务、安全团队和供应链资源。
- 这会让大型项目获得结构性优势。
- 它不符合“发现实用新项目”的产品目标。

这些信息改为单独的“采用风险卡”：

```text
License：缺失
依赖漏洞：2 个高危
安装脚本：包含外部网络访问
供应链证明：未提供
生产使用建议：谨慎
```

只有当安全属于项目承诺的一部分时，才影响主分。例如企业身份系统存在鉴权问题，就属于“没有解决好自己的核心问题”。

## 八、Stars、增长和排行榜

stars 只是影响力信号，不能决定项目质量。

使用原则：

- 使用对数压缩，避免头部项目无限碾压。
- 重点观察 30、90、180 天增长趋势。
- 结合下载量、dependents、fork、Issue 和实际使用信号。
- 识别“真实使用明显高于曝光量”的项目。

项目质量分和排行榜排序分应当分开：

```text
发现排序分 =
  项目价值分 × 75%
  + 最近增长势能 × 15%
  + 曝光不足奖励 × 10%
```

这样可以专门找到：

```text
stars 不高
宣发不足
但真实用户反馈和实际价值很好
```

第一版榜单结构保持克制：

```text
宝藏项目榜   发现高价值、低曝光项目，是产品主榜
经典项目榜   收录长期验证过的成熟项目，与主榜分开
```

“新锐”“小而美”“快速进步”在第一版只作为标签或筛选项，不作为独立榜单。

## 九、缺失数据和置信度

缺失数据不能直接视为零分。

每次分析同时输出：

```text
项目价值：86/100
评估置信度：72%
项目类型：微型 CLI
生命周期：功能完成型
数据时间：2026-07-14
榜单归属：宝藏项目
项目标签：小而美 / 低曝光 / 功能完成型
```

证据不足时降低置信度；只有确认某项能力实际缺失时才扣分。

## 十、为什么使用 Codex

项目分析比账号分析复杂得多，无法只靠脚本完成。

脚本难以自主判断：

- 项目到底解决什么问题
- README 是否名副其实
- 应该如何安装和运行
- 不同技术栈应该执行哪些检查
- 失败是文档问题、环境问题还是项目缺陷
- 一个功能是否真的好用
- 大型系统和微型工具该使用什么不同标准

因此最终选择：

> 使用 Mosoo 中的 Codex Agent 作为分析执行核心。

Codex 负责：

- 理解产品定位和痛点
- 识别项目类型
- 自主制定验证计划
- 克隆、安装、构建和运行项目
- 调用已有工程分析工具
- 操作 CLI、API 或 Web 页面
- 整理证据
- 按项目类型完成评分和报告

脚本从“评分核心”降级为 Codex 可以调用的专业工具。

## 十一、最终技术边界

最终架构已经明确：

> Mosoo 是唯一 Agent Runtime，Codex 是 Mosoo Agent 的执行核心，ghroast 只调用发布后的 Mosoo Agent。

Mosoo 资源拓扑确定为：

```text
现有 ghroast Mosoo App
└── 专用 Cattle 项目评分 Agent
    ├── 专用评分 Skill
    ├── 专用 Environment
    └── 项目分析所需的工具与 MCP 绑定
```

不为项目评分另建 Mosoo App。现有 ghroast App 继续作为整个产品统一的资源、API、运维、日志、用量和成本边界；项目评分通过独立 Agent 及其专用绑定实现职责与运行配置隔离。

```text
用户提交 GitHub URL
    ↓
ghroast 后端创建 Mosoo Thread
    ↓
Mosoo 启动配置为 Codex Runtime 的项目评分 Agent
    ↓
Codex 在 Mosoo 沙盒中分析和运行项目
    ↓
评分 Skill 约束流程、标准和输出
    ↓
Mosoo Thread Events 返回分析进度
    ↓
Agent 返回结构化结果和报告 Artifact
    ↓
ghroast 保存评分并更新排行榜
```

明确不采用：

- Codex SDK
- ghroast 后端运行 `codex exec`
- 后端直接调用 OpenAI API
- 自建 Agent loop
- 自建 planner、tool runner 或 sandbox
- 用大量固定脚本代替 Codex 判断

## 十二、各部分职责

### Mosoo

负责：

- 作为整个 ghroast 产品统一的 App 资源、运维和成本边界
- 发布并运行评分 Agent
- Codex Runtime
- Sandbox
- Thread 与 Run
- 工具执行
- 模型和运行环境配置
- 文件、Artifact 和事件流

### Mosoo Codex Agent

Mosoo Agent 有两种工程契约类型：`cattle` 和 `pet`。其中 `cattle` 在用户界面中显示为 **Task Agent**，项目评分 Agent 必须使用 `kind: cattle`。

原因是项目分析具备明确的任务边界：

- 输入是一个确定的仓库、ref 和评分规则版本。
- 执行过程是一次性的克隆、检查、安装、运行、评估和报告生成。
- 存在明确的成功、失败、超时和取消终态。
- 权威输出是结构化 Artifact，而不是持续对话或角色陪伴。
- ghroast 需要异步跟踪任务状态，并在完成后校验、存储和发布结果。

`pet` 类型更适合持续互动、长期陪伴或开放式会话，不适合作为这条批处理评分链路的运行模型。因此应在现有 ghroast Mosoo App 内创建专用的 `cattle` 项目评分 Agent，不复用现有 `pet` Agent，也不为此另建 App。

该 Agent 绑定专用的评分 Skill、Environment 和必要工具。这里的“专用”表示 Agent 级职责和配置隔离：

- Skill 固化项目类型、评分标准、证据要求和 Artifact Schema。
- Environment 提供安装、构建和运行项目所需的包、初始化脚本和环境配置。
- 工具与 MCP 只绑定项目分析真正需要的能力，避免继承无关资源。
- App 继续统一汇总 ghroast 的资源、运维、日志、用量和成本。

负责：

- 项目理解
- 产品契约识别
- 验证方案制定
- 实际运行和体验
- 证据收集
- 评分判断
- 报告生成

### 评分 Skill

负责：

- 项目分类体系
- 各项目类型的评审标准
- 主评分模型
- 生命周期判断规则
- 证据要求
- 风险说明规则
- 输出 Schema 和报告格式

### ghroast

负责：

- 用户输入界面
- 调用 Mosoo Public Thread API
- 展示 Agent 实时进度
- 读取最终结果和 Artifact
- Schema 校验
- 数据存储
- 榜单计算和展示
- 分享页面

## 十三、建议输出文件

每次分析可以由 Agent 生成：

```text
project-analysis.json
project-report.md
runtime-evidence.json
```

其中：

- `project-analysis.json`：结构化分数、分类、置信度、榜单数据。
- `project-report.md`：面向用户的分析报告。
- `runtime-evidence.json`：安装、构建、运行、测试和操作证据。

## 十四、安全边界

被分析的 GitHub 仓库属于不可信输入。

必须确保：

- 仓库内容只作为被分析数据，不能改变评分 Agent 的指令。
- 仓库内的 `AGENTS.md`、README 和提示词不能覆盖评分规则。
- 所有代码只在一次性 Mosoo 沙盒内运行。
- 沙盒中不放生产密钥。
- 限制网络、CPU、内存和执行时间。
- 安装脚本、postinstall 和预编译二进制均视为不可信代码。
- 分数必须引用实际命令、文件或运行结果作为证据。

## 十五、下一步

下一阶段需要定义三个核心产物：

1. `project-analysis.json` 的完整 Schema。
2. 现有 ghroast Mosoo App 内 `kind: cattle` 项目评分 Agent 的 Skill、Environment、工具绑定和评审工作流。
3. 第一批项目类型 rubric：微型 CLI、SDK、Web 应用、企业平台。

随后可以用一组对照项目验证评分方向：

- 好用但低曝光的小工具
- 高 stars 但体验一般的项目
- 功能完成、长期不更新的小项目
- 活跃但难以使用的大型项目
- 成熟经典项目
- 疑似营销或空壳项目

这组对照测试比一开始精调权重更重要，它能验证产品是否真的会把“隐藏宝石”推出来。
